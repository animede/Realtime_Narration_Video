# Realtime Narration Video テクニカルガイド

[English](technical-guide.en.md) | 日本語

最終更新: 2026-09-28

## 1. 目的

Realtime Narration Videoは、OpenAI互換LLMのストリーミング応答をAivisSpeechで音声化し、LTX-2.5 Audio-to-Videoで約5秒の動画へ変換して順次再生する技術検証アプリです。

最優先指標は、ユーザー送信から先頭動画が再生可能になるまでの時間です。後続動画は再生中に生成し、5秒の再生尺が終わる前に完成させます。

## 2. システム構成

主要コンポーネントは次のとおりです。

| コンポーネント | 役割 |
|---|---|
| FastAPIアプリ | セッション、ストリーミング処理、計測、ファイル配信 |
| OpenAI互換LLM | 会話履歴を使った日本語／英語応答のストリーミング生成 |
| AivisSpeech Engine | 文・節単位のWAV生成 |
| diffusers-movie-server Gateway | LTXバックエンドの排他管理、アセット、生成ジョブ |
| LTX-2.5 | 参照画像と音声から動画を生成 |
| FFmpeg | 元TTS音声のmux、発話用フレームの抽出 |
| ブラウザー | SSE状態受信、発話／待機動画の先読み、二重video要素による切り替え |

処理の依存関係は以下です。

```text
LLM streaming ──→ 文節確定 ──→ TTS ──→ 音声チャンク ──→ LTX生成 ──→ mux ──→ 再生
                       ├──── 次文節TTSを並列実行 ────┘
                       └──── 後続音声を動画キューへ先行投入
```

動画生成は単一GPU上で直列ですが、LLM、複数TTS、生成中の後続音声準備は並列に進みます。

## 3. 起動要件

- Python 3.11以上
- FFmpeg
- 稼働中のdiffusers-movie-server Gateway
- AivisSpeech Engine
- OpenAI互換Chat Completions API

```bash
python3 -m venv .venv
.venv/bin/pip install -e '.[dev]'
cp .env.example .env
PATH="$PWD/.venv/bin:$PATH" ./run.sh
```

ブラウザーで`http://localhost:8782`を開きます。既定URLはlocalhostです。秘密情報と実環境のアドレスは`.env`だけに置き、コミットしないでください。`GATEWAY_PRESET`は既定の`nvfp4-fast`のほか、32GB向けサーバー構成では`nvfp4-32gb`を指定できます。外部オリジンのGUIから利用する場合は`CORS_ORIGINS`をカンマ区切りで設定します（未指定時は`*`）。

## 4. キャラクター登録

`POST /api/sessions`はmultipartでキャラクター画像と設定を受け取ります。

主要フィールド:

| フィールド | 値 |
|---|---|
| `character` | PNG、JPEG、WebP |
| `character_mode` | `standard`または`photoreal` |
| `lip_sync_mode` | `natural`、`balanced`、`medium`、`medium_strong`、`strong` |
| `idle_motion_profile` | `closeup`、`upper_body`、`wide`（既定） |
| `idle_liveliness` | `lively`（既定）または`calm` |
| `idle_pool_size` | 3〜7（既定5）。登録時は常に3本だけ生成 |
| `turn_anchor_mode` | `speaking`（既定）または`idle_frame` |
| `turn_end_mode` | `free`（既定）または`return_idle` |
| `camera_lock_enabled` | 背景基準ECCカメラロック（既定`false`） |
| `video_seed` / `video_steps` | seed 0〜2147483647（既定1004）／steps 1〜12（既定4） |
| `modality_scale_enabled` | 実写会話時の`modality_scale=1.3`を切り替え（既定`false`） |
| `ui_language` | `ja`または`en`。画面表示に使用 |
| `conversation_language` | `auto`、`ja`、`en`。LLM応答と文分割に使用 |
| `video_profile` | UIで選択する公開プロファイル名 |
| `voice_id` | AivisSpeechの話者ID |
| `target_chunk_seconds` | 3.5〜5.0秒 |
| `startup_buffer_chunks` | 再生開始前に待つ動画数 |

登録時にGatewayへ次を送ってLTXを事前ロードします。

```json
{
  "backend": "ltx25",
  "preset": "<GATEWAY_PRESET>",
  "strategy": "coresident"
}
```

同一構成が起動済みならno-opです。`coresident`はH3など別バックエンドを停止せず、LTXのウェイトを併存させます。未ロード時はモデル準備時間が登録処理へ乗り、最初の会話生成へコールドスタートを持ち越しません。

### 4.1 待機動画と実写の発話用アンカー

実写では入力画像の口形が生成結果を強く拘束します。閉口画像を直接参照すると、音声があっても「聞いている人物」として生成されることがあります。

全モードで待機動画（手項5）を作り、実写モードでは発話アンカー（手項1〜4、6〜7）も準備します。

1. AivisSpeechで固定発話を生成（会話言語`en`では「Ah. Ah. Ah. Ah.」、それ以外は「あー、あー、あー、あー。」）
2. 条件用WAVを5.1秒まで無音パディング
3. 選択プロファイルの本来の解像度で準備動画を生成
4. 参照品質と開口成功を優先して8 steps、UI指定seed（既定1004）、`modality_scale=1.3`を使用
5. 待機ループは「待機の動き」設定で2方式を切替える。活発（既定）は往路と、往路終盤から入力画像へFLFで戻る復路を連結する。静かは首尾を入力画像へ錨止めした1本を使う。並進ジャンプ（>5px/フレーム）があればseedを変えて最大3回引き直し、必要な場合だけ背景基準ECCカメラロックを有効化できる。閉口フレームは`character-neutral.png`として抽出する。待機プールの設定値は3〜7（既定5）だが、登録待ちを抑えるため初期生成は常に3本だけである。ブラウザーがプール1周ごとに1本を追加し、設定本数まで漸進成長した後は最新N本を回転させる。6本以上は再生順をランダム化する。非表示タブまたは5分間無操作では追い生成を休止する。任意のセッションで会話が生成中の間は待機プール追加を拒否し、チャット／朗読到着時は全セッションの進行中待機生成を即中断する。
6. 準備動画の0.12秒から軽い開口、0.75秒から大きい開口を抽出
7. 開口度を調整する4段階の発話参照画像として保存

FFmpegの`-ss`は入力指定後に置きます。入力前の高速シークでは、キーフレームが少ない短いMP4が先頭フレームへ戻る場合があります。

待機画面には設定時に生成したシームレスループ動画を表示し、各アンカーはLTXへの内部入力としてだけ使用します。アンカーは後続のフル解像度動画でも繰り返し参照するため、低解像度化しません。先頭動画だけが内部のstartupプロファイルを使用します。

この方針はUIで選べる全24動画プロファイルに共通です。アンカー生成には常に選択プロファイルそのものを使い、startupプロファイルは会話ターンの先頭動画にだけ使います。384×512の実利用では低解像度アンカー版から解像感が改善し、口動作と約2.6秒の会話初動を両立しました。

## 5. 会話パイプライン

`POST /api/sessions/{id}/messages`で会話ターンを開始します。

1. 会話履歴とシステムプロンプトをLLMへ送信
2. ストリーミング中に文末、改行、コロン、日本語の自然な節境界を見つけて発話単位を確定
3. 発話単位ごとにTTSタスクを即時作成
4. 実WAV時間を基に約5秒の動画チャンクへ編成
5. 条件用WAVだけを動画尺+0.1秒まで無音パディング
6. 音声完成順を保って動画キューへ投入
7. LTX生成後、元TTS音声を打ち切らず最終MP4へmux
8. SSEで`playable`を通知し、ブラウザーが先読み・再生

会話入力の先頭に連続する`[動画指示]`は発話文から除外し、そのターンの動画プロンプトにだけ優先適用します。`POST /api/sessions/{id}/narrations`はLLMを通さず、入力文章を同じTTS→LTXパイプラインで直接朗読します。

UI言語と会話言語は独立しています。UI言語はブラウザーの`localStorage`へ保存され、画面を再読込しても維持されます。会話言語の`auto`はLLMへ最新ユーザー入力と同じ言語で返答するよう指示します。英語ではピリオドと単語境界を認識し、日本語より長い文字数で発話単位を構成します。AivisSpeechによる英語の発音品質は選択話者に依存します。

短い先頭発話もLTXでは5秒動画として扱います。発話後の無音区間は後続動画を準備する時間になりますが、次動画が再生可能になった後はブラウザーが現在動画の残りを打ち切り、次の発話へ移ります。音声が5秒を超える場合は映像の最終フレームを維持し、元TTS音声を最後まで再生してから切り替えます。この判定は先頭だけでなく全チャンク境界に適用されます。

## 6. LTX生成パラメータ

高速モードの基本リクエストは次の構成です。

```json
{
  "backend": "ltx25",
  "mode": "a2v",
  "params": {
    "prompt": "<発話内容を含むプロンプト>",
    "width": 288,
    "height": 384,
    "num_frames": 81,
    "fps": 16,
    "steps": 4,
    "guidance_scale": 3.0,
    "seed": 1004
  },
  "extra": {
    "upscale": false,
    "decoder": "vae",
    "audio_start": 0
  },
  "asset_ids": ["<音声ID>", "<画像ID>"],
  "auto_load": true,
  "preset": "<GATEWAY_PRESET>"
}
```

実写で「口動作強調」を有効にした場合だけ、`extra`へ次を加えます。

```json
{"modality_scale": 1.3}
```

### 6.1 scaleの注意点

- `modality_scale`は映像側へ作用し、口領域の動きを強めます。
- `audio_modality_scale`はA2Vでは音声予測側にしか作用せず、音声が凍結されるためno-opです。
- `audio_guidance_scale`もA2Vでは使用しません。
- `modality_scale>1.0`は追加の推論コストを伴います。
- 既定では口開きアンカーを利用し、会話時のscaleを省略します。

## 7. stepsと解像度

会話動画のstepsはUIで1〜12を指定します（既定4）。ターン先頭だけは初動を守るため`min(4, video_steps)`、後続は`video_steps`そのものを使います。実写の発話アンカーと待機動画は品質優先で常に8 stepsです。

| 576×384 | 480×320 | 16 | 81 |
| 384×512 | 288×384 | 16 | 81 |
| 384×640 | 288×480 | 16 | 81 |
| 416×672 | 320×512 | 16 | 81 |
| 416×704 | 320×544 | 16 | 81 |
| 480×640 | 288×384 | 16 | 81 |
| 480×800 | 352×576 | 16 | 81 |
| 800×480 | 576×352 | 16 | 81 |
| 672×416 | 512×320 | 16 | 81 |
| 704×416 | 544×320 | 16 | 81 |
| 640×480 | 384×288 | 16 | 81 |
| 512×384 | 384×288 | 20 | 97 |
| 416×704 | 320×544 | 20 | 97 |
| 480×640 | 288×384 | 20 | 97 |

| 480×320 | 384×256 | 24 | 121 |

## 8. キャラクターモード

| 設定 | 参照画像 | seed | 会話scale | 用途 |
|---|---|---:|---|---|
| 標準 | 同一ターン内で前動画の最終フレームを連結 | UI指定+チャンク番号 | なし | イラスト・3D、映像連続性 |
| 実写・自然 | 毎回`character-neutral.png` | UI指定（既定1004） | 任意で1.3 | 閉口と自然さを優先 |
| 実写・バランス | 毎回`character-speaking-balanced.png` | UI指定（既定1004） | 任意で1.3 | 軽い開口と口動作を両立 |
| 実写・中間1 | 毎回`character-speaking-medium.png` | UI指定（既定1004） | 任意で1.3 | バランスよりやや強い口動作 |
| 実写・中間2 | 毎回`character-speaking-medium-strong.png` | UI指定（既定1004） | 任意で1.3 | 強い設定に近い口動作 |
| 実写・強い口動作 | 毎回`character-speaking.png` | UI指定（既定1004） | 任意で1.3 | 口が動かない場合の最終手段 |

旧`fast`値は既存セッションとの互換性のため受理し、大開口アンカー・scaleなしとして扱います。

ターン開始を`idle_frame`にすると、送信瞬間の待機フレームをブラウザーがキャプチャし、先頭チャンクの参照画像にします。ターン終了を`return_idle`にすると、最終チャンクの末尾を元のキャラクター画像へFLF錨止めします。両方を有効にすると待機→会話→待機のポーズ連続性を優先できます。既定は`speaking` / `free`で、口動作と自由な動きを優先します。

調整後のキャラクターは`POST /api/presets`で設定、待機プール、発話アンカーごと保存できます。`POST /api/presets/{id}/restore`は保存ファイルを新規セッションへコピーするため、再生成なしで即時復元します。保存先は`NARRATION_DATA/presets/`です。

## 9. クライアント再生

ブラウザーは2つの`video`要素を交互に使用します。

- 再生中に次のMP4を`preload=auto`で準備
- 現在の`currentTime`が`speech_duration`へ達したら固定尺の残りの無音を必ず打ち切る
- 次動画が未完成なら閉口した待機ループへ切り替え、完成通知後に発話動画へ戻す
- 次チャンクが`playable`になった時点で非表示側へロード
- 現在動画の`ended`で即座に切り替え
- ターン開始時は待機映像またはキャプチャした待機フレームで前ターン映像を覆う
- 待機動画も2つの`video`要素で次クリップを先読みデコードし、同じ入力ポーズでハードカットする
- チャンクごとにMP4/WAVのダウンロードリンクを表示
- セッションIDを`localStorage`へ保存し、リロード後に状態を復元
- 実測の切り替え時間を画面へ表示

後続の生成処理全体が5秒未満なら、理論上は動画間ギャップが発生しません。

会話ターン中はGatewayのリアルタイム優先リース（TTL 60秒、20秒ごとに更新）を保持し、H3など長尺ジョブの滑り込みを防ぎます。リースAPIのない旧Gatewayでもベストエフォートで動作します。また、SSE視聴者が0のまま5秒経過した実行中ターンは、次のチャンク境界で自動キャンセルします。

## 10. 計測

各セッションの`session.json`に次を保存します。

- LLM開始、最初のdelta、完了
- TTS開始、音声完成
- 動画開始、再生可能化
- サーバー申告の生成秒数
- profile、steps、seed、frames、modality scale
- 発話時間とタイムライン位置

主要指標の計算:

```text
LLM初動       = llm_first_delta_at - llm_started_at
TTS時間       = audio_ready_at - tts_started_at
動画処理全体  = video_ready_at - video_started_at
先頭完成      = first.video_ready_at - llm_started_at
後続再生余裕  = previous.video_ready_at + previous.duration - next.video_ready_at
```

正の再生余裕は次動画が前動画終了前に完成、負の値はその秒数だけ不足することを示します。

解像度比較には`scripts/benchmark_resolution.py`を使用できます。比較時は同一画像、音声、prompt、seed、steps、frames、scaleを固定し、A/Bの開始順を反転してください。

## 11. 代表性能

2026-09-04時点の実写、384×512選択、先頭4 steps／後続8 steps、GPU TTS、ロード済み状態の代表値です。現行の既定は後続も4 stepsで、値は性能回帰比較用の参考として残しています。

| 指標 | 1回目 | 2回目 |
|---|---:|---:|
| LLM最初の文字 | 0.115秒 | 0.139秒 |
| 先頭TTS | 0.231秒 | 0.224秒 |
| 先頭サーバー生成 | 2.170秒 | 2.057秒 |
| 先頭動画完成 | 2.734秒 | 2.657秒 |
| 後続サーバー生成 | 3.359秒 | 3.292秒 |
| 後続再生余裕 | 1.436秒 | 1.507秒 |

実測値はGPU負荷、モデルのロード状態、入力画像、音声長、prompt長で変動します。コールドスタートと定常性能は分けて評価してください。

## 12. 運用上の注意

### HTTP 409

Gateway管理外のバックエンド、生成中の排他切り替え、競合要求が原因になります。LTX/H3はGatewayだけで管理してください。

### コールドスタート

LTXプロセスが起動していても、最初の生成でモデルが遅延ロードされる場合があります。実写のキャラクター準備生成がこのコストを吸収します。標準モードはバックエンドロードだけを行うため、構成によっては最初の会話生成に遅延ロードが残ります。

### AivisSpeechのGPU

`--use_gpu`だけでなく、ONNX Runtime CUDA ProviderがcuDNNをロードできていることを確認します。APIがCUDA対応を返しても、依存ライブラリ不足でCPUへフォールバックする場合があります。プロセスが`nvidia-smi`へ表示され、CUDA Providerと`libcudnn.so.9`がロードされていることを確認してください。

GPU化直後の最初の合成にはモデル初期化が乗る場合があります。アプリ利用前に短い文を1回合成してウォームアップします。定常時の短文合成は開発環境で約0.18〜0.23秒でした。

### 実写の口が動かない

確認順序:

1. `character-speaking.png`が実際に開口しているか
2. 会話リクエストがそのアンカーを参照しているか
3. `steps`がサーバーで有効か
4. 高速モードで失敗する場合は口動作優先を選ぶ
5. 音声アセットとA2Vモードが正しいか

### 無音時も口が少し開く

発話用アンカーの副作用です。現構成では発話失敗の防止と速度を優先しています。必要なら口動作優先との比較、アンカー抽出時刻、無音区間の後処理を個別に検証してください。
