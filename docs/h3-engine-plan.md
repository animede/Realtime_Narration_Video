# H3 エンジン統合プラン(設計のみ、2026-10-05)

r-n-v(Realtime Narration Video)の動画エンジンとして、LTX-2.5 に加えて
MiniMax-H3 ref2va(diffusers-movie-server の `dual-realtime-ref2va` /
`-32gb` プリセット、commits 579b761〜bc73e5c)を選べるようにする設計。
**実装は未着手。本ドキュメントは手法の確定のみ。**

## 1. 何が良くなるか(導入動機)

- **リップシンク品質**: LTX-2.5 のプロンプト駆動の口動作に対し、H3 ref2va は
  vocal_lock(音声 latent を x0 固定)で TTS 波形に口形が直接追従する。
  実測で口の開閉・"o" 形まで出る(2026-10-05 検証)。
- 速度は実測で成立済み: 7.3 秒クリップを cadence 6.47s(96GB 構成)/
  6.91s(32GB 構成・352×608)。5.9 秒クリップなら 4.9〜5.9s。
- トレードオフ: 初回応答レイテンシは LTX(最短 2.6s)より不利(§5)。

## 2. 全体方針

r-n-v のエンジン依存部は実質 `app/gateway.py`(backend="ltx25"・mode="a2v"・
interrupt 先がハードコード)と `app/config.py`(GATEWAY_PRESET)に閉じている。
ここに **engine 抽象("ltx25" | "h3")** を導入し、チャンク生成の意味論を
マッピングする。orchestrator / chunker / muxer の構造は変えない。

## 3. 概念マッピング(LTX → H3)

| r-n-v の概念 | LTX-2.5 | H3 ref2va | 備考 |
|---|---|---|---|
| 発話チャンク生成 | mode=a2v(アンカー画像+音声) | mode=ref2va(参照画像+音声、vocal_lock) | 1:1 対応 |
| 発話アンカー画像 | 毎チャンクの開始フレーム | 参照画像(同一性の源) | **同一画像の再利用が latent/prefix キャッシュのヒット条件**(H3 側実装済み)。アンカー再利用運用がそのままキャッシュ戦略になる |
| 音声差し替え(TTS を mux し直す) | r-n-v 側で実施 | **不要**(H3 が原音を mux 済み、波形相関 0.997) | muxer の H3 分岐はパススルー |
| 待機(idle)クリップ | a2v or i2v | **fl2va で first=last=アンカー画像**(ループ可能クリップ。2026-10-06 probe 済み: 先頭/末尾がアンカーへ 33dB で復帰、継ぎ目目立たず、口閉じ・同一性維持、定常 24.5s/本 @352×608・5s・turbo 4step → 登録時に5本 ≈2分) | base transformer 使用(リアルタイム最適化対象外)。**アンカーは必ずキャンバス寸法へ事前 cover-crop**(first は stretch / last は cover-crop と前処理が非対称で、寸法不一致だとループが閉じない)。所作の大きさ・画質は**ユーザー目視で許容済み(2026-10-06)**、プロンプト調整不要 |
| fps プロファイル(16/20/24) | 24 プロファイル対応 | **24fps 固定**(runner 定数)。フレーム数は 17n+5 丸め | H3 選択時は fps 選択 UI を 24 固定に。クリップ長グリッド: 3.04s(73f)/ 4.46s(107f)/ 5.875s(141f)/ 7.29s(175f) |
| 先頭チャンク低解像度 | 同画角系の低解像度 | 低フレーム(73f)+ 低解像度で代替 | §5 |
| ターン内のフレーム連結 / FLF 錨止め | i2v / flf2v で姿勢連続 | **不可**(ref2va は開始フレーム錨を持たない。fl2va は別チェックポイントでスコープ外) | チャンク境界はジャンプカット許容。緩和は §7-1 |
| 中断 API | /ltx25/api/interrupt | h3 側の中断 API(gateway 経由。movie-server 2026-08-25 追加の interrupt を h3 パスで) | エンジン別 interrupt 先の抽象化 |

## 3b. プロファイルとプリセット互換(H3 固有の制約)

- **fps は 24 固定**(runner 定数)。LTX の 16/20/24fps 選択は H3 では無効。UI は
  H3 選択時に fps を「24 固定」表示にし、省コスト調整は解像度側で行う。
- **解像度は 32 の倍数**かつ、リアルタイム成立は画素予算で決まる
  (実測: ~215k px = 32GB 級 / ~246k px = 96GB 級、7.3s チャンク時)。
  LTX の 24 プロファイルは流用せず、H3 専用プロファイル表を定義する:
  | 画角系 | 32GB 級 | 96GB 級 |
  |---|---|---|
  | 縦型 | 352×608(検証済み) | 384×704(検証済み) |
  | 横型 | 608×352(外挿、要1回確認) | 704×384(同) |
  | 4:3 系 | 512×384 / 384×512(同) | 544×416 相当(同) |
- **チャンク長は 17n+5 フレームのグリッド**(3.04 / 4.46 / 5.875 / 7.29s)に
  丸まる。chunker の目標長はグリッド値に合わせる(§4-2-3)。
- **エンジンはキャラクタープリセットの同一性の一部にする**: プリセットは
  設定+アイドルプール+発話アンカーを保存するが、アイドルプールの絵柄と
  解像度はエンジン固有。エンジンを切り替えたプリセット復元は
  (a) アイドル再生成+解像度の近傍マップを伴う明示的な「変換」操作にするか、
  (b) プリセットをエンジン別に持つ(推奨: 実装が単純で事故がない)。

## 4. 必要な変更一覧

### 4-1. gateway(diffusers-movie-server)— 調査済み(2026-10-06)、前提修正

**調査の結果、gateway は h3 ジョブを自前で直列化していない**(h3 はジョブごとに
worker スレッドを生やして同期 POST するだけで、同時実行の上限判定はバックエンドの
生成ロック(/api/status の busy)のみ)。DECODE_STREAM 有効時は denoise 完了で
busy=False になるため、**gateway 経由でも2本目は decode 窓に受理される見込み**
→ **実測で確認済み(2026-10-06)**: gateway 経由の cadence **6.42s** vs 直叩き 6.44s
(352×608・7.0s・dual-realtime・n=9、差は揺らぎ以内)。**コード変更なしで cadence は出る**。
ただし2つの症状を実測で確認:
(a) progress の誤帰属は全ジョブで再現(前ジョブが decode 中に 0.95→0.05 へ後退、
    新ジョブ初回が前ジョブの 0.95 を拾う)→ 補正1は必要性確定。
(b) 「202 受理直後に次を投入」すると 2/3 のジョブが backend 409 で failed になる
    (gateway の受理は backend 着手を保証しない)。**投入規律「前ジョブが backend で
    走り出したのを確認してから次を投入」なら失敗ゼロ** → r-n-v クライアントは
    この規律で実装する(gateway 側の補正2はその後でも可)。
また backend/load の overrides に **H3_PORT 指定が必須**(テスト環境での知見)。

したがって「同時枠2の新設」は不要で、重なり運用で壊れる **4 点の補正**だけ入れる(案C):
1. **進捗の誤帰属**: /api/progress はグローバル1個で job_id を gateway が見ていない。
   2本目の denoise 進捗が decode 中の1本目に混入 → _refresh_h3 で補正
   (簡易版: 後続 running があれば progress=max(0.95))。
2. **409 の窓**: gateway の busy 確認〜バックエンドのロック取得に窓があり、worker の
   POST が 409 を即 failed にする → overlap 有効時のみ短時間再試行。
3. **busy の死角**: backend/load・unload・other_busy が「decode 中の h3」を busy と
   見なさず、decode 中のプロセス停止や ltx25 の割り込みが通る → procman の
   backend_busy を「status.busy or gateway の running h3 ジョブあり」に拡張。
4. **interrupt の ID**: job_id 省略(=denoise 中を止める)は overlap でも正しく動くが、
   統一 job_id 指定は h3 側と不一致 → 必要なら backend_job_id の紐付け(任意)。

overlap 判定は /api/status の `runner.decode_stream && decode_deferred_active` から
取る(adopted プロセスでも判定可能。プリセット env 依存にしない)。
非 overlap プリセットは全補正の対象外で従来どおり完全直列。
変更規模: jobs.py ~40-60 行 + procman.py ~10-15 行、バックエンド無変更。
任意の安全弁: overlap 時 inflight>=2 で 409(decode 待ちの滞留防止)。
実装手順・検証項目の詳細は調査報告(2026-10-06)を参照。

### 4-2. r-n-v

1. `app/config.py`: `VIDEO_ENGINE`("ltx25" 既定 / "h3")、
   `H3_GATEWAY_PRESET`("dual-realtime-ref2va" / "-32gb")、
   `H3_RESOLUTION`(96GB: 352×640、32GB: 352×608)、
   `H3_REFERENCE_SHORT_EDGE=1024`。
2. `app/gateway.py`: engine 別の backend/mode/interrupt/パラメータ組み立て。
   H3 は `{"backend":"h3","mode":"ref2va","seconds":<wav長>,"num_inference_steps":4,
   "reference_image_short_edge":1024,...}` + 参照(アンカー画像+チャンク wav)。
3. `app/chunker.py`: H3 選択時のチャンク目標長をティアで切替 —
   96GB: `target_chunk_seconds=5.875`(141f、cadence 4.9s で余裕)、
   32GB: `7.29`(175f、cadence 6.91s)。17n+5 丸めはサーバ側が行うので、
   r-n-v は「丸め後クリップ長 ≥ 音声長」だけ保証(現行の実 WAV 長ベースの
   編成がそのまま使える。クリップ末尾の無音余りは既存の「最終フレーム保持」
   ロジックと同じ扱い)。
4. 起動バッファ判定: 実測 LTX 生成時間の代わりに H3 の cadence 実測値を使う
   (既存の動的開始判定に エンジン別の計測値を流すだけ)。
5. キャラクター登録時のプリワーム(§5)。
6. UI: エンジン選択(キャラ種別 or セッション設定)、H3 時は fps=24 固定表示。

### 4-3. バックエンド(minimax-h3)— ほぼ変更なし

- 実装済みの機能のみで成立する見込み。唯一の確認点: **無音 wav の ref2va**
  (idle 用)と **短フレーム(73f)の cadence/品質**は未実測(§6)。

## 5. レイテンシ設計(H3 の弱点への対処)

送信→最初の動画の最短は LTX 2.6s に対し、H3 は denoise だけで 4〜6s
(141f/175f)。対処:

1. **登録時プリワーム**(効果最大): キャラクター登録時に
   (a) プリセットロード + ダミー1本生成 → torch.compile(+10〜13s)と
   prefix KV / 参照 latent キャッシュを事前に温める。以後の全チャンクが
   キャッシュヒット+コンパイル済みで走る。r-n-v の「登録時に LTX を
   事前ロードしアンカー生成」と同じ流儀。
2. **先頭チャンクを 73f(3.04s)**: 実測済み(2026-10-06、ユーザー目視で品質
   問題なし): ウォーム後 wall **4.6s**(denoise 2.3 + decode 1.6)@352×608。
   107f=6.6s / 141f=8.6s とフレーム数に比例。短尺の破綻なし(3 seed)。
   バックエンド側は `H3_MIN_SECONDS=3.0` が必要(commit dda2fa5、既定 5.0 のまま。
   プリセット env か r-n-v の backend/load overrides で指定)。
   現行の「先頭は min(4, steps)・低解像度」ポリシーの H3 版。
3. 1本目を待つ間は既存の待機プール再生がそのまま時間を稼ぐ。

## 5b. H3 重みを VRAM へ載せるタイミング(2026-10-06 決定)

前提: バックエンドは「プロセス起動(~45s、VRAM ほぼゼロ)」と「重みロード
(初回生成時)」が分離しており、さらに H3 の重みは2系統ある
(fl2va=base transformer 34GB / ref2va=リアルタイムスタック 27〜50GB+初回 compile)。

採用: **選択時はプロセスのみ、重みは登録時、会話経路は裏でプリワーム**の3段階。
1. **エンジン選択時**: gateway backend/load でプロセス起動のみ(重みは載せない)。
   LTX へ戻すのはプロセス kill だけで実質ノーコスト → 選択の往復が気軽にできる。
2. **キャラクター登録時(=最初のアイドル生成)**: fl2va の重みをロードし
   アイドルプール+発話アンカーを生成。既存の「登録時プリロード」UX と同じ場所
   なので新しい待ち時間を作らない。
3. **アイドルプール完成直後**: ref2va スタックを裏でプリワーム(73f ダミー1本で
   compile+prefix/latent キャッシュを温める)。待機動画の再生中に完了し、
   最初の会話ターンに ~30s のロード+compile が乗るのを防ぐ。

同居の可否: 96GB 機は LTX nvfp4(33GB)+ H3 低VRAM(27.3GB)= 60GB で同居可
(フル H3 49.8GB でも 83GB で理論上可、未検証)→ エンジン切替は瞬時、生成は
gateway 実行ゲートが直列化。32GB 機は同居不可 → 切替は完全スワップ(数十秒〜1分)
になるため、この3段階設計(選択を軽くする)が特に効く。

## 7. リスクと割り切り

1. **チャンク境界の姿勢ジャンプ**(ref2va に開始フレーム錨がない): まず
   許容(アンカー参照で同一性は保たれ、構図ジャンプのみ)。緩和候補は
   (a) プロンプトに姿勢の標準形を書く (b) 境界 2〜3 フレームのクロスフェード
   (c) 将来 fl2va pruned(Kijai 配布あり)の追加検証 — いずれも後続。
2. **GPU 配置**: H3 realtime は GPU0(50GB or 27GB)+ GPU1(6GB)。
   Aivis(TTS)は GPU1 残量で共存可(このマシン)。32GB 級ターゲットでは
   TTS/LLM 非同居の前提を README に明記(LTX nvfp4-32gb と同じ条件)。
3. **LTX との併存**: 96GB 機なら coresident 可能性あり(H3 50GB + LTX 33GB
   は要検証)。当面は「セッション開始時にエンジン選択 → gateway がプリセット
   切替(数十秒)」のモデルで十分。
4. H3 は 24fps 固定・17n+5 丸めのため、LTX の 16/20fps 省コスト運用に相当する
   手段がない(解像度で調整する)。
5. 品質系の未検証: 無音 idle、73f 短尺、アニメ調キャラ(実測は実写系1人のみ)。
